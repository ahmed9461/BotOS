## قراءة العقد

قُرئت وحدةAccountCoordinator وBotConversations وخدمةTelegramFiles وMediaProtocol وLiveBotPanel وLiveBotViewModel وBotOsApplication والمخطط المثبت منcontract61. بصمة المخطط والإصدار لم يتغيرا.

messageSendOptions.sending_id هوint32 غير دائم؛ يرجع داخلmessageSendingStatePending، ولا يعتمد عليه بعد إعادة تشغيل العملية لربط رسائل عشوائية. updateMessageSendAcknowledged ليس وصولًا نهائيًا. inputPhotoحده10MB ومجموع أبعاده10000 ونسبة20؛ inputVideo يتوقعMP4/H264؛ inputVoiceNote يقبلOGG/Opus/mono أوMP3/M4A بحسب المخطط المثبت. يستخدم التسجيلM4A/AAC/mono دون ترميز أو صلاحيات أوسع من الحاجة.

## الترتيب ومسؤوليات المكونات

1. CaptureTarget منBotConversations بعد تحققReadyAccount وchatTypePrivate/userTypeBot، يتضمنChatKey وجيل العرض ومعرف الحساب والشات والاسم المعروض. لا مسار أوchatId من نص المستخدم. قبل فتح المنتقي وعند رجوعه وعند التأكيد ومباشرة قبلRPC يتحقق الهدف؛ التبديل يلغي المعاينة ولا يرسل إلى بوت جديد.
2. مخزن مرفقات داخلnoBackupFilesDir/telegram/main/files/botos_outgoing، بحصة200MiB/32عنصرًا وحد50MiB للملف. ينسخContentResolver URIاختاره المستخدم بشكل متدفق خارجMain. ملف الصورة يعادJPEG بأبعاد≤1600، دونEXIF،≤10MiB ونسبة20 ومجموع10000. يفحص نوع الفيديو الحقيقي بـMediaExtractor/MetadataRetriever؛MP4/H264كفيديو، والآخر يعرض خيارالإرسال كملف بوضوح دون ترميز مكلف خفي. صوت معروف كصوت؛ملف غيرقابل للتشغيل لايعطى نجاحًا زائفًا.
3. سجل ذري محلي صغير قبلRPC، بملف داخلي ذيUUID ومعرفsending_idعشوائي موجب غير متكرر وaccountId/chatId وحالة ومعرف الرسالة إن عُرف. لا محتوى الصوت/الصورة أوcaption في السجل. فساد السجل يفشل بوضوح ولا يمسح سجلًا أو ملفات قد تكون قيد الرفع.
4. خدمةTelegramUploads مستقلة عن عمر الشاشة، تراقبupdates للحساب الحالي فقط. تربطtemporary messageId منالاستجابة أوupdateNewMessage، وتعالجالنتيجةالنهائية التيقدتسبقردالطلب. الحالات النهائية لا تتراجع بفعلردpendingقديم. بعداستعادةالعمليةgetMessageللمعرفاتالمعروفةفقط؛ المجهوليبقىغيرمؤكد، دونإعادةsend. فشلالطلبأوالمهلةليسإذنًالحذفالملف. الحصةتخليالمكتملالمؤكدفقط،لاالمعلقأوغيرالمؤكد بالوقت.
