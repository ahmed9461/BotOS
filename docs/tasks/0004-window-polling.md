# ملحق 0004 — إزالة تداخل مزامنة اختبار النافذة

2026-09-18. الحالة: planned قبل التعديل. نقطة البداية 89351f43 على feat/telegram-runtime. الطلب: الاستمرار وتسليم التطبيق بعد جاهزيته مع بقاء التصميم المعتمد.

## الدليل والتشخيص

قُرئت حزمة BotOS-runtime-checks-7 من التشغيل 35377793103، وبصمتها c3f9e92cf62db1149683ebc982866dbd38ccebfd9590e0a10a023da3b309aecb مطابقة. XML تثبت 21 حالة JVM وثماني حالات JNI/Keystore ناجحة بلا فشل أو تخطي. اختبارات الواجهة توقفت عند 0/3 حتى المهلة؛ التشغيل ككل فاشل. تشغيل Android رقم20 توقف بالطريقة نفسها، فلا نعد إعادة تشغيله إصلاحًا.

المصدر أضاف ui.runOnIdle { ui.activity... } داخل انتظار النافذة وIME. getter الخاص بـactivity يستدعي ActivityScenario.onActivity، والذي يفرغ main looper عند استدعائه من main. هذا تداخل مزامنة قابل للتعليق، وليس قراءة View عادية. المصدر الرسمي: https://raw.githubusercontent.com/android/android-test/main/core/java/androidx/test/core/app/ActivityScenario.java ، https://developer.android.com/reference/kotlin/androidx/compose/ui/test/junit4/AndroidComposeTestRule . عدم توفر stack dump يمنع الجزم بأن هذا السبب الوحيد؛ يعالج ثم يختبر.

## التنفيذ بالترتيب

1. قراءة حالة النافذة في callback واحد لـscenario.onActivity من خيط الاختبار، بلا runOnIdle متداخل أو الاحتفاظ بمرجع Activity بعد recreation. استخدام snapshot للأرقام والـfocus/IME فقط.
2. تسجيل مراحل الاختبار الثابتة بلا محتوى مستخدم، مع الإبقاء على اللمسة الفعلية والكيبورد الحقيقي وعتبة -2..12dp والست تبديلات واختبارات الاستعادة.
3. تشغيل نفس اختبارات JVM21 وJNI/Keystore8 وUI3 دون تخفيف الشروط أو تعديل الإنتاج أو التصميم أو الأيقونة.
4. قراءة XML وnative-runtime واللقطات وقياس الكيبورد، ثم تحديث الذاكرة وTESTING والخطط والسجل. لا بدء شريحة ربط الحساب قبل نجاح هذه البوابة.

## القبول والتراجع

إنهاء الاختبارات كاملة لا مجرد التجميع. لا تكرار تلقائي حتى ينجح فحص متذبذب ولا تعطيل lint. التراجع بcommit الاختبار فقط؛ لا تغيير لبيانات أو أسرار أو إصدار الاعتمادات. بيانات التطبيق الحقيقية وشاشة تسجيل الدخول ليست ضمن هذا الإصلاح.
