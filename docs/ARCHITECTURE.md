# البنية المعمارية

آخر مراجعة: 2026-09-18. توجد خمس وحدات فعلية. التنفيذ الحالي معاينة محلية؛ نقل Telegram الحقيقي مرحلة لاحقة.

## التدفق وحدود الوحدات

`UI intent → ViewModel → Repository/Gateway → immutable state → Compose`

- `:core:model`: نماذج Kotlin/JVM مستقلة عن Android، وتطبيع الأسماء وقواعد هوية الرسائل وعزل الحالة وحماية الأفعال القديمة.
- `:core:telegram`: عقد Gateway وتنفيذ PreviewGateway المصطنع. لا TDLib أو JNI أو تسجيل دخول حقيقي بعد.
- `:core:data`: DataStore للأسماء والترتيب والتفضيلات، بنسخة واحدة لكل ملف؛ لا سجل رسائل دائم مكرر.
- `:core:designsystem`: الألوان والأشكال والحركة والرموز المشتركة. أصول أيقونة launcher منفصلة ومحفوظة كما أقرها المالك.
- `:app`: نقطة التجميع، وحالة العرض، ووجهات التنقل، والشاشات ومحرك عرض المحتوى.

عند الربط الحقيقي يكون المسار `TDLib update → adapter → normalized message/action → per-chat state → renderer`. لا يمر JSON الخام أو كائن TdApi إلى الواجهة. عمليات الشبكة والتخزين خارج مسار رسم الواجهة. لا تضاف وحدات فارغة أو طبقات عامة لمجرد التوسع النظري.

## مصادر الحقيقة

DataStore مسؤول عن الاسم المحلي والترتيب والتفضيلات. TDLib عند تنفيذه سيكون مسؤولًا عن الجلسة والمحادثات والرسائل والملفات. ViewModel يملك حالة العرض والانتظار ونتائج الأفعال والمسودة المؤقتة. لا تستخدم أسماء التبويبات بدل معرفات account/chat؛ لا تتسرب أفعال بوت إلى بوت آخر.

تبقى مفاتيح التخزين الحالية ثابتة في الجولة 0003. لا مسح للتفضيلات أو للأسماء من أجل إصلاح العرض.

## التنقل وقراءة الحالة

Navigation 3 يملك سجل الشاشات المحفوظ. الوجهات الجذرية الحالية: المساحة، المكتبة، المظهر؛ ووجهة إضافة أو تعديل اسم بوت. رجوع النظام يغادر واجهة التطبيق ولا يضغط زر الرجوع داخل البوت.

**قاعدة الجولة 0003:** يقرأ كل Route حالة الشاشة عبر `collectAsStateWithLifecycle` داخل محتوى NavEntry. لا تعتمد وجهة محتفظ بها على لقطة Preferences محسوبة خارجها. يجمع مستوى التطبيق الإعدادات العامة للثيم، وتجمع وجهة المظهر الإعدادات نفسها لعرض عناصرها. لا تستخدم تغيير المفتاح أو إعادة إنشاء الشاشة قسرًا كحل لحالة قديمة.

تظل مسودة المعاينة في SavedStateHandle. حالة التمرير وعناصر المحرر محلية محفوظة ضمن عمرها، وليست أرشيفًا دائمًا للمحادثات. لا ترسل `/start` عند فتح كل تبويب؛ بدء المحادثة فعل صريح عند الحاجة بعد تنفيذ النقل الحقيقي.

## مساحات النظام ولوحة المفاتيح

يمتلك BotOsApp وحده اتحاد مساحات systemBars وdisplayCutout وIME. يطبق `windowInsetsPadding` مرة واحدة، مع `contentWindowInsets` صفرية في Scaffold، ثم يستهلك padding الخاص بمحتواه. لا تضيف الشاشات أو composer مساحة الكيبورد أو التنقل مجددًا.

عند ظهور الكيبورد يختفي شريط التنقل تمامًا ويتقلص رأس المساحة؛ لا يحجز مكان لشريط مخفي. يرسم لون خلفية الثيم قبل المساحات لضمان اتساق حواف الشاشة. استخدام isImeVisible يقبل ExperimentalLayoutApi في موضعي الاستخدام فقط؛ لا تعطيل عام لتحذيرات المترجم.

## المحتوى الديناميكي

معرف الرسالة مرتبط بالحساب والمحادثة ورقم المراجعة. تعديلات الرسالة تستبدلها وأزرارها في المكان نفسه. لا تنفذ الأفعال القديمة على مراجعة جديدة، ولا تستنتج callback من نص الزر. تبقى بيانات الأفعال وترتيبها الأصلي محفوظين؛ اتجاه العربية يؤثر في العرض لا معنى الفعل.

النموذج الداخلي يدعم كتل النصوص والجداول والتفاصيل والأزرار. ليس هذا ادعاء توافق كامل مع Telegram Rich Messages، ولا يتحول Markdown عادي إلى نوع بروتوكول مزعوم. الأنواع غير المدعومة لها حالة واضحة بدل انهيار أو زر كاذب.

## الأداء والاختبارات

قوائم كسولة ومفاتيح مستقرة وحدود لعدد الرسائل والكتل وعمقها. تجنب تحريك ارتفاع تقرير طويل كامل عند كل تحديث؛ تحريك الحجم لأقسام الطي الصغيرة فقط. لا تحميل تلقائي لوسائط كبيرة. لا بلوغ مفترض لـ60 أو120 إطارًا؛ القياس على إصدار مناسب وجهاز معروف بوابة مستقلة.

اختبارات النواة منفصلة عن اختبارات Compose على جهاز. فحص ثبات الأيقونة والتباين وملكية المساحات يكمل اختبار التشغيل ولا يستبدله. انظر TESTING وخطة 0003 للأدلة الفعلية.
